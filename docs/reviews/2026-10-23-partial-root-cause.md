# Partial 및 지연 원인과 해결 가능성 검토

2026-10-23. 현재 작업 트리, 수정 전 `325d302`, 공개 FreeRTOS 입력과 일반 C 합성 입력을 비교했다.
원본 사용자 펌웨어는 이 환경에 없다. 제품 수정·한도 상향·배포는 이번 조사에서 수행하지 않았다.

## 판단

**불필요한 Partial과 지연은 개선할 수 있다. 단순한 타임아웃 조정 문제가 아니라 작업 예산, 조건부 프로그램 복제, 호출자 정보 병합이 연결된 구조 문제다.**

우선 예산 소진 후 낭비를 제거하고, 서로 다른 호출자의 객체가 한 함수의 256개 한도를 채우지 않도록 분석 경계를 바로잡아야 한다. 구문 구조 공유는 재파싱과 메모리 비용을 줄이는 후속 단계다.
실제로 한 호출이 256개보다 많은 객체에 도달하면 현재 보호 한도에서 불완전 결과가 필요하다. 모든 Partial을 숨기는 것은 완료 기준이 아니다.

## 1. 공용 예산을 매크로가 소진해 상세 콜백 추론이 시작부터 막힘

`src/analyzer.ts:406`에서 하나의 `AnalysisWorkBudget`을 만들고 매크로와 콜백에 전달한다.
`src/analysis-budget.ts`의 프로젝트 누적 상한은 1,000,000이며 함수 상한은 100,000이다.

현재 전체 656개 파일의 계측 결과:

- 매크로 작업량: **1,004,519**
- 콜백 표현식 평가 작업량: **2**
- 상세 콜백 추론 관계: **0**
- 최초 예산 초과: 매크로 단계, `xPortIsAuthorizedToAccessBuffer`, `portable/GCC/ARM_CM33_NTZ/non_secure/port.c:2053`
- 이후 콜백 단계의 최초 평가: `callback_example.c:21`, `bbb`의 초기값 평가에서 바로 프로젝트 예산 초과

수정 전 소스도 매크로 1,004,550 / 콜백 2 / 추론 0으로 같은 문제가 있었다.
따라서 `Callback project work limit reached`가 콜백 전파 자체의 대량 계산을 뜻하지 않는 경우가 확인됐다.
여기서 작업량은 `inferPointerCalls`의 평가와 매크로 토큰 스캔이다. 기본 관계·리터럴 인자·등록 콜백 처리 등 모든 계산의 CPU 시간을 나타내는 수치가 아니다.

## 2. 예산 소진 후에도 상당한 환경 계산을 계속함

프로파일러를 끈 현재 소스 계측에서 매크로 단계는 **21.23초**, 최초 프로젝트 예산 초과는 단계 시작 **6.39초** 후였다.
즉 예산 소진 뒤에도 약 **14.84초**가 더 걸렸다. 결과는 여전히 불완전했다.
이후 처리에는 기본 참조 보존도 포함되므로 14.84초 전부가 즉시 절감 가능한 시간이라고 단정하지 않는다.

원인 경로:

1. `src/macro-expansion.ts:42`는 예산 초과 시 현재 확장 대안을 중단한다.
2. `src/project-analysis.ts:161`은 다음 파일의 include 타임라인을 계속 구성한다.
3. `src/project-analysis.ts:165` 이후 매크로 환경 구성·정의 참조 조회도 계속한다.
4. 이 환경 탐색과 조건 보완 계산은 토큰 작업 예산에 포함되지 않는다.

CPU 프로파일의 큰 비용은 `outsideBranches`, `combineBranches`, include 방문과 GC였다.
이 입력의 확장 C 재파싱은 약 **0.45초**였다. SECOND Comment의 사용자 입력에서 재파싱이 주된 비용이었던 사실을 모든 입력에 일반화할 수 없다.
조건 추적을 추가한 현재 코드의 환경 계산 비용이 수정 전보다 증가한 것도 확인했다.

## 3. 전체 폴더의 플랫폼·설정 후보가 크게 섞임

전체 입력에는 `portmacro.h` 후보 **161개**, `FreeRTOSConfig.h` 후보 2개가 있다.
정확한 상대 경로로 해소되지 않은 include는 같은 파일명 후보를 모두 탐색한다(`src/project-analysis.ts:71`).

전체 실행에서:

- 219개 파일: `Macro include/event limit reached`
- 132개 파일: `Macro environment alternative limit: 32 candidates`
- 25개 파일: `Macro expansion alternative limit: 32 candidates`
- 272개 파일: 매크로 작업량 한도로 일부 미확장

포트 하나와 `heap_4.c`만 남긴 35개 파일에서도 원본 프로그램 **324개 → 파생 프로그램 3,244개**, 재파싱 **3,460회**였다.
매크로가 예산 **813,707**, 콜백이 **186,294**를 사용한 시점에 중단됐다.

설정 헤더도 하나로 줄인 33개 파일 대조에서도 **321개 → 3,283개**로 늘었다.
매크로 단계 약 **2.58초**, 후속 콜백 단계 약 **47.25초**였다. 단순히 포트·설정 후보만 줄이면 해결되는 문제는 아니다.
이 직접 분석 계측은 Worker 메모리 보호를 적용한 배포 환경의 응답 시간 보장이 아니다.

## 4. 여러 호출자의 객체가 공통 함수 요약에서 합쳐져 256개 한도를 채움

`src/pointer-targets.ts:975`는 모든 호출 지점의 인자를 함수 하나의 `target.params[n]`에 합친다.
`src/pointer-targets.ts:365`의 `invalidate`는 이 합쳐진 인자로부터 실제 객체와 포인터를 따라간다.
그러므로 한 호출이 작아도 다른 호출자들의 객체가 같은 도달 영역 한도를 사용한다.

FreeRTOS 포트 하나만 남기고 매크로 없이 콜백을 분석해도 약 **15.90초**, 7라운드 후 8개 파일에서 영역 한도 경고가 남았다.
예를 들어 `xCoRoutineCreate`의 보존 영역에는 `heap_4.c`의 할당 관련 객체와 `ucHeap`이 들어갔고, 처음 누락한 경로는 다른 함수의 `tasks.c` 객체 `.xStateListItem`이었다.

이 증상만으로 모든 경로가 불필요하다고 판정하지 않았다. 대신 프로젝트 이름과 무관한 C 합성 입력으로 원인을 분리했다.

| 호출자 수 | 호출 한 번의 객체 수 | 모든 객체 수 | 공통 helper 사용 | 영역 한도 |
|---:|---:|---:|---|---|
| 8 | 9 | 72 | 공유 | 없음 |
| 32 | 9 | 288 | 공유 | **256 도달** |
| 32 | 9 | 288 | 호출자별 helper | **없음** |
| 1 | 257 | 257 | 공유 또는 분리 | **256 도달** |

동일한 객체와 연산을 유지하면서 helper 공유 여부만 바꾼 대조다. 32개 호출 상황이 섞여 생긴 한도와 실제 한 호출의 상한 초과를 구분한다.
재현: `npx tsx docs/reviews/2026-10-23-partial-context-repro.ts`
이 파일은 현재 원인의 진단용 재현이며 해결됐음을 주장하는 테스트가 아니다.

전체 콜백 전용 대조에서는 객체 탐색·무효화(`invalidate`, `matchingRegions`, `regionPath`)와 GC가 CPU 상위였다.
640 MiB 보호를 적용한 직접 분석에서는 약 16초 후 메모리 한도에 도달했다. 보호를 적용하지 않은 별도 대조는 90초 조사 제한으로 중단했다.
따라서 매크로를 끄는 방식도 전체 해결책이 아니다.

## 5. 해결 접근 비교

| 접근 | 기대 효과 | 한계 | 판단 |
|---|---|---|---|
| 예산 소진 시 중단·원인 표시만 수정 | 소진 후 낭비와 잘못된 원인 해석 감소 | 상세 분석 누락은 남음 | 먼저 적용할 작은 수정 |
| 분석 범위를 필요한 폴더로 제한 | 플랫폼·헤더 후보와 작업량 감소 | 33~35개 파일에서도 Partial 재현 | 보조 수단 |
| 분석 단위·호출 상황·조건부 IR 개선 | 불필요한 예산 소진과 인자·영역 혼합, 복제 비용을 함께 줄임 | 단계별 정확성 검증이 필요한 구조 변경 | **권장하는 본 해결 방향** |

### 권장 순서와 완료 기준

1. **예산 중단 경계와 원인 진단** — 환경 계산까지 포함해 소진을 감지하고 불필요한 다음 작업을 중단한다. 매크로 예산 소진을 콜백 비용 문제처럼 안내하지 않는다. 이 단계만으로 Partial 해결이라고 하지 않는다.
2. **전체 작업량 상한과 진행 정책 분리** — 전 단계가 공용 예산을 쓰면 후속 분석이 사실상 0회가 되는 정책을 고친다. 예산을 두 배로 만드는 방식만으로 해결했다고 판단하지 않는다. 일정 작업량은 재개 가능한 배치·의존성 기반 작업 목록으로 처리하고, 실제 완료와 중단을 구분해야 한다.
3. **호출자 객체와 공통 변경 요약의 경계 수정** — 매개변수에 대한 기호적 효과를 유지하면서 실제 호출자의 객체를 공통 256개 한도에 전부 합산하지 않도록 한다. 필요할 때만 제한된 호출 상황을 구분한다. 모든 호출자를 무제한 복제하지 않는다.
4. **조건부 공통 구문 공유** — 같은 구조를 재파싱·실행하는 비용을 줄인다. 숫자 인덱스, 조건 선택의 상관관계, 별칭과 원본 위치를 보존해야 한다. 현재 `choice` 값들을 독립적으로 합치기만 하면 안 된다.
5. **완료성 검증 강화** — 작고 명확한 입력은 `complete=true`와 필요한 콜백 후보를 필수로 검증한다. 현재 FreeRTOS 테스트는 Partial을 허용하므로 안전한 중단·관계 유지 검증이지 전체 분석 완료 검증이 아니다.

필수 회귀 기준:

- 대규모 무관한 매크로 작업 뒤의 독립 콜백이 앞 단계 예산 때문에 분석에서 사라지지 않는다.
- 32명 × 9개 객체의 공통 helper는 256개 상한을 불필요하게 넘지 않는다.
- 한 호출이 실제로 257개 객체를 다루면 한도와 불완전 상태가 유지된다.
- `table[PICK][PICK]()`은 서로 다른 선택을 섞어 교차 콜백을 만들지 않는다.
- 알려진 합성 입력과 실제 대상에서 cold/warm, 후보·불확실성, 단계별 시간·최대 메모리를 비교한다.

## 범위와 남은 확인

작은 예산·중단 수정은 구현 가능성이 높다. 문맥 혼합 제거는 일반 C 재현으로 개선 여지를 확인했지만 실제 분석기 안에서의 수정은 아직 검증하지 않았다.
조건부 IR 공유와 재개 가능한 전파는 분석 구조 변경이므로 한 번에 통째로 교체하지 않고 위 완료 기준으로 단계별 검증해야 한다.
원본 펌웨어의 50초 사례와 256개 경로를 해결했다고 주장하지 않는다. 이번 결과는 구체적인 원인과 구현 가능한 개선 지점을 확인한 것이다.

## 6. 승인 후 구현과 검증

구현 상태와 설정 변경은 [analysis.md 7절](../../analysis.md#7-후속-구현-smart-analysis와-partial-경계)에 기록했다. 앞 절의 원인 조사는 수정 전 기록으로 보존한다.

- Copilot은 로컬 전파 OFF와 독립적으로 명시적 허용 범위를 분석한다. 범위 밖 호출은 제외 수로 보고한다. 새 Smart Analysis Include/Exclude가 Macro(로컬 전파 포함)와 Copilot을 함께 제어하며, 두 기능의 스위치는 독립적이다. 새 Include 저장 전까지 옛 범위를 읽어 호환한다.
- 기본 전체 작업량은 누적 배치 계수로 이어 간다. 함수별 누적 상한·메모리·Stop·구조적 상한은 유지한다. 명시적인 고정 프로젝트 예산을 주입한 경우 다음 파일의 include 환경과 재파싱을 중단한다. 디스크 체크포인트나 이벤트 루프 배치 스케줄러를 구현한 것은 아니다.
- 공유 함수가 빌려 쓰는 실제 인자 영역을 공통 기호 요약의 256개 제한과 분리하고, 겹치는 실제 객체의 중복 탐색을 막았다. 문맥은 최대 64개로 제한한다. 32×9 재현은 거짓 상한이 없고 실제 257개 재현은 한도를 유지한다.
- 조건부 변형에서 완전히 동일한 불변 구문만 공유한다. 값·위치·지역 변수·호출 ID와 전체 선택의 상관관계를 유지하며 서로 다른 대안의 파싱은 유지한다.

단일 포트·매크로 OFF 입력은 15.90초/영역 경고 8개 파일에서 11.31초/한도 경고 없음으로 바뀌었다. 수정 후 값은 CPU 프로파일링을 포함한 단일 측정이다. 단일 포트·단일 설정 매크로 ON은 진단용 45초 Stop 시에도 Partial이었다. 서로 다른 조건과 구조적 한도를 모두 제거했다고 판정하지 않는다.

전체 656개 파일을 **1024MiB old-generation 제한 Worker**에서 검증한 결과, 소스 준비 6.57초와 상세 분석 37.81초 후 메모리 보호로 정상 반환했다. 최대 샘플 heap은 약 645MiB, 상세 추론 참조 1,254개, 확장 참조 3,296개였으며 강제 Stop이나 OOM 크래시는 없었다. 직접 헤더·조건·변경 한도는 남아 **complete=false**다. 이전의 0개 상세 추론과 달리 후속 콜백 단계가 실제 실행됐음을 보여주지만 전체 속도 개선이나 원본 펌웨어 완료를 보장하지 않는다.

정확한 소형 Worker 입력은 cold/warm/disk restore/한 파일 저장에서 모두 complete=true와 필요한 후보 6개를 유지했다. cold 상세 약 34ms, warm 상세 약 1ms, 디스크 복원 약 117ms였다. 원본 private 펌웨어와 WSL/Windows 빌드 환경은 이번 실행에서 확인하지 않았다.
