# 콜백 영역 계산 재사용 수정과 검증

2026-10-23. 비교 기준은 `26925de`의 Worker/분석기와 이번 영역 계산 재사용 수정이다. 기존 `analysis.md`와 남은 비용 조사 문서를 보존했다. 배포 버전·설정·분석 한도는 변경하지 않는다.

## 변경

- 한 번의 `inferPointerCalls` 실행에서 같은 저장소 경로를 반복 분해하지 않는다. 읽기 전용 경로 배열만 재사용하고 4096개가 차면 비운다. 후보·값·읽기 결과·무효화 결과는 이 캐시에 저장하지 않으며 다음 분석 실행으로 넘기지 않는다.
- 빈 영역 집합의 조회와 이미 존재하는 영역 키의 트리 재등록을 생략한다. 기존 키의 stamp/definite/exported/context/shallow 정보는 계속 갱신하고 조회 시 현재 맵에서 읽는다.
- 구체적인 일반 객체는 기호 매개변수 해소를 생략한다. `$arg:` 경로는 기존 의존성 기록·실제 인자 해소를 유지한다. 바이트 범위 쓰기는 구체적인 배열 원소도 `byteDestination`으로 포함 배열까지 넓혀야 하므로 이 생략을 적용하지 않는다.
- 영역/변경 256, 공급 문맥/후보 64, 루프·작업량·메모리·Stop 보호를 유지했다. 분석 의미가 같으므로 캐시 호환 버전은 **9**를 유지한다.

수정 범위는 `src/pointer-targets.ts`의 기존 함수 내부다. 새 분석 엔진·설정·프로젝트별 예외를 추가하지 않았다.

## 실패 재현과 회귀

같은 중첩 배열 필드에 opaque 변경 → 명시적 콜백 대입 → 호출을 반복하는 입력에서, 8회/80회 반복의 경로 파싱은 수정 전 **389/3845회**였다. 후보 8개/80개는 원래도 모두 완전했으므로 정확성 수정으로 표현하지 않는다. 새 작업량 회귀는 수정 전에 이 증가로 실패했다.

수정 후 경로 파싱은 두 입력 모두 **6회**이며 같은 후보·완전성·경고 없음이 유지됐다. 시간 임계값 대신 실제 경로 파싱 횟수를 검사한다.

추가 회귀는 다음을 확인한다.

- 동일한 배열 필드의 조회 → wildcard 무효화 → 정확한 덮어쓰기 → 재무효화에서 `first` / 미확인 / `second` / 미확인을 각 원본 호출 위치에서 보존한다.
- 4200개 독립 객체로 캐시 용량을 넘긴 뒤에도 첫/마지막 경로가 정확하며, 같은 URI의 소스를 바꿔도 이전 콜백 값이 남지 않는다.
- 기존 32×9 공유 호출자는 거짓 영역 한도가 없고 실제 1×257은 한도를 유지한다. 별칭·와일드카드·독립 객체·생략된 효과·바이트 쓰기·실제 구조적 한도의 기존 회귀도 유지한다.

## 수정 전후 Worker 결과 비교

사전 보관한 Worker와 새 Worker에 같은 다섯 합성 파일을 넣었다. 반복 쓰기 600회, 32×9 공유 호출자, 실제 257개 영역, wildcard 쓰기 순서와 4200개 경로를 포함한다.

cold / warm / 디스크 복원 / 한 파일 저장 모두 **전체 호출 참조 1851개, 추론 참조 606개**가 동일했다. 이름 개수만 비교하지 않고 전체 call record를 깊게 비교했으므로 대상 ID·원본 위치·조건·추론 근거·불완전 플래그도 포함한다. 경고와 완료 여부도 동일했다. 실제 한도 사례를 포함하므로 이 입력 묶음의 완료 여부는 **partial**이다.

이전 Worker가 저장한 캐시를 새 Worker에서 복원하는 교차 대조도 같은 결과를 유지했다. 기존 분석 캐시를 강제로 버리거나 사용자 확인 대상을 초기화할 필요가 없다.

## 완료되는 합성 입력 성능 대조

콜백 필드 16개를 가진 객체에 변경·정확한 대입·호출을 1000회 수행했다. 새 Worker를 매번 띄워 수정 전/후 순서를 번갈아 3회씩 측정했다. 각 실행은 경고 없이 완료하고 추론 참조 **1000개**, 전체 호출 참조 **2000개**의 내용이 동일했다.

| 중앙값 | 수정 전 | 수정 후 |
| --- | ---: | ---: |
| 상세 요청 반환 | 218.10ms | 180.18ms |
| 최대 샘플 힙 | 47.91MiB | 47.84MiB |

이 입력의 반환 시간은 약 **17.4% 감소**했다. 최대 샘플 힙은 비슷하다. 공개 대형 트리나 원본 펌웨어의 성능 개선율로 일반화하지 않는다.

## 공개 입력과 남은 한계

앞선 감사와 동일한 지문의 단일 포트·설정 FreeRTOS 33개 파일을 새 Worker로 실행했다. 매크로 약 3.09초, 콜백 약 41.91초였으며 진단용 45초 취소로 여전히 **Partial**이다. 샘플 힙 약 258MiB다. 이번 수정으로 전체 지연·Partial이 해결됐다고 판단하지 않는다. 서로 다른 진행 지점에서 잘린 결과를 같은 완성 결과의 속도나 정확도로 비교하지 않는다.

별도 직접 분석에서는 두 버전에 같은 **진단용 고정 작업량 800000**을 적용했다. 두 실행 모두 매크로 673862 + 콜백 126139 = 총 800001에서 멈췄으며, **전체 호출 참조 10394개와 파일별 경고 600개가 동일**했다. 이 값은 제품 기본 작업량 정책을 변경한 것이 아니며, 같은 작업 지점의 부분 결과 보존을 확인한 대조다. 45초 실행에 추가로 보인 영역 경고만으로 의미 변경을 단정하지 않는다.

## 검증과 검토

- typecheck/build, 단위 **614개**, Worker/cache/workspace **62개**, 메모리 **6개**, 집중 콜백 회귀 **150개**, 두 브라우저 UI 검사와 실제 macOS Extension Host 검사가 통과했다.
