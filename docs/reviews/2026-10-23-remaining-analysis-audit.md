# 남은 매크로·콜백 비용의 최신 코드 재측정

2026-10-23. 측정 대상은 `26925de`이며 제품 소스·설정·보호 한도는 변경하지 않았다.
원본 private 펌웨어 대신 로컬 공개 FreeRTOS 체크아웃과 기존 합성 입력을 사용했다.

## 1. 이번에 확인한 결과

**공유 호출자의 거짓 영역 한도 수정은 유지된다. 전체 포트 입력의 매크로 비용과 단일 포트 입력의 콜백 전파 비용은 최신 코드에도 남아 있다.** 범위를 줄이는 것만으로 상세 분석 완료를 보장하지 않는다.

아래 수치는 새 Worker에서 한 번씩 측정한 값이다. 반복 측정 중앙값이나 수정 전후 성능 개선 수치가 아니다. 두 full 실행은 진단용 45초 취소가 적용된 부분 결과이므로 후보 개수를 완성 결과의 정확도 비교에 사용하지 않는다.

| 입력 | 파일 | 소스 파싱 | 상세 요청 반환 | 매크로 단계 | 콜백 단계 | 최대 샘플 힙 | 결과 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| 전체, Macro + 콜백 | 656 | 7.41초 | 45.64초 | 34.39초 | 7.95초 | 607MiB | 진단 취소, Partial |
| 전체, 매크로만 분리한 진단 | 656 | 7.32초 | 37.93초 | 34.25초 | 0.30초 | 544MiB | 취소 없이 반환, 매크로 한도로 Partial |
| 단일 포트·단일 설정, Macro + 콜백 | 33 | 0.71초 | 45.16초 | 3.57초 | 41.43초 | 249MiB | 진단 취소, Partial |

‘소스 파싱’은 개별 소스 요청 구간, ‘상세 요청 반환’은 derive 요청·기본 연결·결과 전달 등을 포함한 구간이다. 매크로/콜백 단계는 Worker 진단의 단계별 값이므로 두 단계의 합이 상세 요청 전체와 같지는 않다. 매크로 전용 진단에도 기본 관계 처리를 위한 콜백 단계 진입은 남는다. 사용자 설정을 새로 추가한 실행 모드가 아니다.

### 입력과 실행 조건

- macOS arm64, Node `v22.22.2`, 현재 소스로 `npm run build` 후 실행.
- FreeRTOS 체크아웃 HEAD `640d0c43705e64cd53f46b31d882de6cd8433933`. 로컬 추가 파일 `callback_example.c`를 포함한다. `.vscode`는 C/H 입력에 포함하지 않는다.
- 전체 입력에는 `portmacro.h` 161개, `FreeRTOSConfig.h` 2개가 있다. 실제 단일 빌드의 선택된 입력과 구분한다.
- 전체 두 실행의 상대 경로·내용 지문은 동일하다: `0c49f109abd2fffc54ee964032af0adec178b383a3c9004c8a69baf45528635a`.
- 33개 대조는 `portable/GCC/ARM_CM4F`, `portable/MemMang/heap_4.c`, `examples/coverity/FreeRTOSConfig.h`를 남기는 기존 진단 선택 규칙이다. 제품 코드의 프로젝트별 예외가 아니다. 지문: `b81f1bd1e2285f547e1c978e6d66026b4449684ced1d1bf27f8d65efd5b441a6`.
- Worker old-generation 제한 1024MiB와 제품 메모리 보호를 유지했다. 45초는 이번 조사용 취소이며 제품의 기본 타임아웃으로 넣지 않았다. 두 full 실행은 메모리 보호 발동 전에 조사 취소됐고, OOM 오류 없이 반환했다. 샘플 힙을 총 RAM 또는 절대 최대 메모리로 해석하지 않는다.

## 2. 남은 경고

전체 두 실행은 include/event 한도 219개 파일, 환경 대안 32개 한도 134개 파일, 확장 대안 32개 한도 120개 파일이 동일했다. 매크로 전용 실행에서도 약 34초가 남으므로 전체 지연을 콜백 탓으로만 설명할 수 없다.

33개 대조에는 환경 대안·확장 대안 한도가 각각 9개 파일에 남았다. 콜백에는 루프 4회, 공급 문맥 64개, 변경 슬롯 256개 경고가 각 1개 파일에서 나왔고, 이후 진단 취소됐다. 후보가 없다는 뜻이나 경고가 모두 오탐이라는 뜻은 아니다.

## 3. 콜백 비용의 다음 조사 위치

기존 직접 계측기에 `PROGRESSIVE=1 MEMORY_MIB=640 DEADLINE_MS=12000 PROFILE=1`을 주고 같은 33개 입력을 별도로 프로파일링했다. 이 실행은 Worker 시간 비교용이 아니며 12초 진단 취소까지의 CPU 표본이다.

8396개 표본의 self sample을 같은 함수명·파일별로 합친 결과:

| 함수 | 표본 비중 |
| --- | ---: |
| GC | 11.6% |
| `invalidate` | 9.7% |
| `regionPath` | 8.5% |
| `matchingRegions` | 7.1% |
| `share` | 4.8% |
| `containsRegion` | 4.6% |

프로파일 실행에는 확장 재파싱 3486회, 재파싱 누적 약 1.74초가 기록됐다. 큰 표본 비중은 다음 계측 우선순위를 정하는 근거이며 각 함수가 잘못 동작한다는 증명은 아니다.

후속 수정은 **콜백의 영역 경로 비교·조회·무효화에서 반복 작업을 계수로 재현하는 것**부터 시작하는 편이 구체적이다. 같은 경로가 반복 처리되는 원인과 정확성 보존 조건을 확인한 뒤 중복 제거를 검토한다. 별칭·wildcard 인덱스·쓰기 순서·실제 257개 한도를 보존해야 한다. 매크로 쪽은 많은 헤더 후보의 환경 구성·조건 대안 비용을 별도로 조사한다. ELF 심볼 조회나 AI 요청을 추가하면 이 반복 계산이 자동으로 없어지는 것은 아니다.

## 4. 기존 수정의 보존 확인

- `npx tsx docs/reviews/2026-10-23-partial-context-repro.ts`: 6개 조합 통과. 8×9 및 32×9는 공유/분리 helper 모두 거짓 영역 한도 없음. 실제 1×257은 두 경우 모두 한도를 유지하고 필요한 `target` 후보도 보존했다.
- `npx tsx test/analysis-performance.ts --mode=full --fixtures --output=artifacts/remaining-analysis-audit/fixture-lifecycle.json`: cold/warm/disk restore/한 파일 저장 모두 `complete=true`, 필요한 추론 참조 6개 유지. 오류 없음. 기존 검사는 이 실행에서 이름 집합과 cold 개수를 단언하며, 이번 요약의 나머지 단계는 저장된 결과에서 개수와 완료 상태를 확인했다. 위치·조건·불완전 플래그 전체의 동등성 검사를 새로 실행한 것으로 보고하지 않는다.
- 이번에는 전체 단위/UI/Windows/WSL 검사를 다시 실행하지 않았다. 제품 수정이나 출시 검증을 완료한 작업으로 표현하지 않는다.

원시 결과와 진단용 실행기는 로컬 `artifacts/remaining-analysis-audit/`에, CPU 프로파일은 `artifacts/partial-investigation/audit-current-full-one-config.cpuprofile`에 보관한다. artifacts는 기존 정책대로 Git에서 제외된다. 원본 펌웨어의 시간·메모리·완료성은 계속 미검증이다.
