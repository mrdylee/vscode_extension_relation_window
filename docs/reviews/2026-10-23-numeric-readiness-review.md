# Numeric dependency/readiness review

검토 대상: `c069c06`의 숫자 의존성 시작점 제거와 진단 변경.
비교 기준: `0f0c1e0`, 기존 공개 0.1.75 Worker, 해당 구현 커밋.
현재 브랜치를 유지하고 합성 C·실제 Worker·브라우저 검사로 검토했다.

## 발견 및 수정

### [P1] 동일한 멤버 타입 정보의 지수적 중복 확장

`src/pointer-targets.ts`의 `dependencyLayouts`가 각 타입 대안의 멤버 레이아웃을
그대로 이어 붙였다. 조건부 구조체 대안이 같은 하위 타입으로 합류해도 중복이
남아 다음 멤버 단계에서 다시 복제됐다. 깊이 4/8/12/14의 합성 입력에서 멤버
검사 횟수가 **46/766/12286/49150**으로 증가했다. 이 증가는 새 proof 안에서
발생하며 일반적인 식 방문 계수만으로 제한되지 않는다.

동일한 캐시 레이아웃 객체만 중복 제거했다. 서로 다른 객체의 타입·조건·필드
대안은 유지하며 실제 콜백 흐름이나 후보 집합을 합치지 않는다. 수정 후 같은
입력의 검사 횟수는 **16/32/48/56**이다. 기존 코드의 파일당·메모리·분석 한도를
상향하지 않았다. 실제 원본 프로젝트의 메모리 경고 원인을 재현한 것은 아니다.

회귀는 시간 임계값 대신 깊이 6→10에서 `RelationIndex.layout` 호출 수의
증가율을 검사한다. 수정 전 **239→3139**로 실패했고 수정 후 통과했다.
대상 콜백 보존과 분석 경고가 없다는 조건도 함께 확인한다.

### [P2] 파일 범위 한도와 Worker 중단의 진단 누락

10001개 중 10000개만 색인해도 상세 입력 세대는 최신이고 콜백 한도는 없을
수 있다. 기존 새 진단 로직은 이 경우 `current`를 표시했다. Worker 중단과
캐시 재구축 필요 상태도 `preparing`으로 표시될 수 있었다.

현재의 파일 수 한도 플래그를 진단에 전달해 `current (partial)` 판정에 넣었다.
Worker 오류 역시 Partial에 반영한다. 인덱싱·파일 갱신·관계 계산은 `preparing`,
사용자 조치가 필요한 대기 사유는 `blocked`로 구분한다. 분석 준비 자격이나
Copilot 범위를 넓히지 않았다. 작은 범위로 재구축하면 한도 플래그가 사라진다.

## 검증

- 타입 대안·별칭·정수 선택자·조건식 부작용과 실제 256개 한도 회귀를 유지했다.
- 간접 함수 호출에 숫자 조회를 전달하는 별도 대조에서 이전/현재 Worker의
  후보 이름·원본 위치·조건·불완전 플래그는 같았다. 정밀한 런타임 타깃 증명은 아니다.
- 타입 중복·파일 한도·Worker 중단·캐시 대기 표시를 수정 전 실패로 확인했다.
- typecheck/build, 단위 **611개**, Worker/cache/workspace **62개**, 메모리 **6개**,
  두 브라우저 UI 검사가 통과했다.
- 소형 입력의 여섯 필수 콜백은 cold/warm/disk/save 모두 완료되며 후보의 이름,
  원본 위치·조건·불완전 플래그도 동일했다.
- 실제 macOS Extension Host 통합 검사도 exit 0으로 통과했다.

캐시 호환 버전 9와 기존 보호 한도를 유지한다. 공개 버전 태그·배포 파일은
변경하지 않았다. 원본 펌웨어와 Windows/WSL 실환경은 이 검토에 포함되지 않는다.
