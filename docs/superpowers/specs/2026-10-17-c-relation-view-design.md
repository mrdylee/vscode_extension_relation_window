# C Relation View + Context View 설계 초안

## 목적과 확정 요구사항

- 기존 C 코드를 이해하기 위한 VS Code 확장이다.
- Source Insight 4.0의 Relation Window와 Context Window를 함께 사용하는 탐색 경험을 재현한다.
- 함수 이름뿐 아니라 호출하는 파일, 줄 번호, 실제 호출 코드를 표시한다.
- Relation View는 함수·변수 등 심볼의 종류를 노드 이름 앞의 서로 다른 아이콘으로 구분한다.
- 메인 코드창에서 함수 이름을 한 번 클릭하면 그 함수를 기준으로 관계 창이 자동 갱신된다.
- 관계 창의 노드나 참조 위치를 선택하면 Context View에 해당 코드와 위치가 표시된다. 단순 선택으로 메인 코드창을 이동하지 않는다.
- 사용자가 몇 단계 위의 호출자까지 볼지 선택할 수 있다.
- 관계 창에서 키보드로 선택한 노드를 확장하고, 해당 노드부터 추가로 펼칠 단계 수를 지정할 수 있다.
- 다양한 개발 환경의 소스 폴더를 빌드 없이 열어 사용할 수 있어야 한다.
- 컴파일러, SDK, compile_commands.json, 별도 언어 확장의 설치를 기본 사용의 필수 조건으로 만들지 않는다.
- `#if 0`처럼 비활성이 확실한 조건부 영역을 분석에서 제외하는 옵션을 제공한다. 제안 기본값은 제외이며, 전체 소스 탐색을 위해 해제할 수 있다.

현재 문서는 브레인스토밍 초안이다. 실행 가능한 확장이나 프로젝트 전체의 관계 정확도를 검증한 결과는 아직 없다. 작은 C 예제의 구문 추출은 [구현 가능성 검토](../../research/2026-10-17-feasibility.md)에서 실행 확인했다. 원본 기준은 Source Insight 4.0이며, 두 창의 연동과 사용자 제공 사진을 기준으로 설계한다. 함수 탐색 이외의 원본 전체 기능까지 구현하기로 확정한 것은 아니다.

## 원본 확인과 사진에서의 관찰

- 공식 Context Window 문서는 코드에서 함수 호출을 클릭하면 정의를 표시한다고 설명한다. Context Window Options는 Relation Window의 선택도 추적한다고 명시한다.
- 공식 Relation Window 문서는 커서 아래 심볼 추적, 그래프 노드 확장·접기, 기본 확장 깊이 Levels, 선택 노드의 Expand Special을 설명한다.
- Expand Special의 단계 수는 전체 그래프의 루트가 아니라 선택한 노드 기준이다.
- 사용자가 제공한 사진에서 메인 코드창은 상단, Context Window는 하단 왼쪽, Relation References는 하단 오른쪽에 있다. Context Window에는 함수 선언으로 보이는 줄이 강조되어 있다.
- 사진의 References를 직접 호출만 의미하는 것으로 해석하지 않는다. 호출, 선언, 함수 주소 참조 등 위치 종류를 분리하여 탐색할 수 있어야 한다. 같은 이름 노드가 여러 개라는 사실만으로 재귀 호출이라고 판정하지 않는다.
- 공식 문서에서 위 확장 기능과 메뉴는 확인했으나 사용자가 사용한 확장 키의 정확한 조합은 아직 확인되지 않았다. 특정 키를 원본 기본값이라고 단정하지 않는다.

## 제안하는 첫 사용 흐름

1. 소스 폴더를 열면 그 안의 .c와 .h 파일을 백그라운드에서 읽는다. 분석 중과 완료 상태를 구별한다.
2. 메인 코드창에서 B 함수 이름을 클릭하면, 바깥 함수가 A이더라도 B가 Relation View의 기준이다. Context View에는 B의 정의를 미리 표시한다.
3. 관계 창은 관련 함수와 위치를 노드로 묶어 표시한다. 같은 함수 안의 여러 호출을 생략하거나 하나로 합치지 않는다.
4. 각 위치에는 작업 폴더 기준 파일 경로와 1부터 시작하는 줄 번호를 표시한다. 선택한 위치의 실제 코드와 앞뒤 문맥은 Context View에서 읽는다.
5. 함수 제목을 선택하면 Context View에 정의를, 호출·참조 위치를 선택하면 해당 위치를 강조해 표시한다. 선택에 따라 메인 코드창이나 그래프 루트를 바꾸지 않는다.
6. 깊이 1은 직접 호출자, 깊이 2는 직접 호출자를 부르는 함수까지 표시한다. 루트는 깊이 0이다.
7. 노드별 펼치기와 접기를 지원한다. 깊이를 늘려도 재귀와 순환은 반복해서 무한 확장하지 않는다.
8. 선택 노드에서 키보드 또는 우클릭 메뉴로 한 단계 더 펼치거나 추가 N단계를 지정해 펼친다. 키보드로 선택을 옮겨도 Context View가 따라온다.
9. 자동 추적을 잠시 고정하여 메인 코드창에서 새 심볼을 선택해도 탐색하던 관계를 유지할 수 있다.
10. 실제 편집 위치를 옮기려면 별도의 소스 열기 동작을 사용한다. 제안 조작은 더블클릭 또는 Enter이다. 이 조작 역시 현재 관계의 루트와 확장 상태를 보존한다.

자동 추적 기준은 사용자가 설명한 대로 커서 아래에서 선택한 함수이다. 빈 공간이나 분석 불가능한 이름을 선택하면 이전 결과를 유지하고, 어떤 함수의 결과인지 제목으로 명확히 표시한다. 제안 기본값은 사진에 맞춘 References 모드, 깊이 1이다.

Relations의 루트, Relations에서 선택한 항목, Context의 미리보기 위치는 서로 다른 상태이다. Context의 스크롤·텍스트 선택이나 관계 노드 선택을 메인 코드의 새 심볼 선택으로 취급하지 않는다. 늦게 도착한 과거 선택의 응답이 최신 Context 내용을 덮어쓰지 않도록 한다.

## 화면 예시

아래 이름과 위치는 동작 설명을 위한 가상 예시이다.

```text
┌────────────────────────────────────────────────────────────┐
│ 메인 코드창: check_fault(state); ← 함수 이름 클릭           │
├──────────────────────────────┬─────────────────────────────┤
│ Context View                 │ Relation View               │
│ control.c:80                 │ check_fault                 │
│   if (ready) {               │  ├─ control_task            │
│ >   check_fault(state);      │  │   ├─ control.c:80 [선택] │
│   }                          │  │   └─ control.c:125       │
│                              │  └─ fault.h:15 [선언]       │
└──────────────────────────────┴─────────────────────────────┘
```

위 그림의 선은 개념적인 계층을 나타낸다. 실제 Relation View는 사용자 사진을 기준으로 가로 방향의 노드와 연결선으로 표시한다.

기본 배치는 메인 코드창 아래에 Context 왼쪽, Relation 오른쪽으로 두 영역이 동시에 보이도록 제안한다. VS Code의 구체적인 배치 방식은 기술 검증으로 결정한다. 두 영역의 폭은 조절 가능하게 한다.

Context View는 읽기 전용 코드 미리보기로, 구문 색상, 줄 번호, 파일 경로, 선택 위치 강조와 스크롤을 제공한다. 정의가 여러 개면 파일별 후보를 표시하고 사용자가 선택하도록 한다. 분석 결과가 없거나 파일이 삭제되면 그 상태를 표시하고 오래된 코드를 현재 결과로 유지하지 않는다.

### 심볼 종류 아이콘

- 노드 이름 앞에 분석으로 확인한 종류의 아이콘을 표시한다. 함수와 변수는 반드시 서로 다른 형태로 구분한다.
- 표시 대상에 포함되는 구조체·타입, 매크로 등도 종류별 아이콘을 사용한다. 종류를 판별하지 못한 항목에는 공통 미확인 아이콘을 사용하고 함수로 단정하지 않는다.
- 색상만으로 구분하지 않고 아이콘 형태, 툴팁 및 접근성 이름으로 종류를 전달한다. 실제 아이콘 도안은 구현 시 선택한다.
- 심볼 종류와 관계 종류는 별개다. 함수 주소를 담은 변수나 함수 포인터 테이블은 변수 아이콘으로 표시하며, 함수 주소 참조라는 관계를 직접 호출과 구분한다. 함수 선언은 함수 종류를 유지하되 선언 위치임을 별도로 표시한다.
- 이 요구사항은 그래프에 나타나는 심볼의 표시와 분류에 적용한다. 일반 변수의 전체 참조 탐색이나 구조체 타입 추론까지 구현 범위를 자동으로 넓히지는 않는다.

첫 버전은 두 창의 연동, 함수 호출자와 함수 참조 탐색, 단계 확장이 중심이다. References는 직접 호출·선언·함수 주소 참조를 구분해 보여주며, Callers는 직접 호출만 표시한다. 호출자가 있는 항목은 해당 함수를 다음 확장의 기준으로 삼고, 선언처럼 호출자가 없는 위치는 끝 항목으로 둔다. 피호출자 및 양방향 동시 보기, 일반 변수 참조, 구조체 타입 해석, 데이터 흐름 추적, 그래프 내보내기는 별도 확장 범위로 남긴다.

## 분석 방식 비교와 추천

| 방식 | 장점 | 요구사항과의 관계 |
| --- | --- | --- |
| 내장 C 구문 분석기와 호출 위치 인덱스 | 빌드 설정 없이 소스에서 호출 구문과 범위를 수집 가능 | 추천. 파일 간 대상 판별과 모호성 처리는 직접 구현·검증해야 함 |
| 기존 언어 서버 호출 계층 사용 | 빌드 환경이 맞으면 의미 분석 결과를 활용 가능 | 기본 사용의 유일한 분석 수단으로 두기 어려움 |
| 텍스트 검색 중심 | 빠르게 시제품을 만들 수 있음 | 선언·주석·문자열·매크로를 호출과 혼동하므로 주 분석 방식으로 부적합 |

기술 후보는 Tree-sitter의 C 문법이다. 소스 구문 구조를 읽는 기능을 재사용하며 C 파서를 새로 만들지 않는다. 내장 WASM으로 작은 C 예제에서 호출 구문과 위치를 얻는 것은 실행 확인했다. Tree-sitter 자체가 함수의 실제 연결 대상이나 실행 경로를 해결해 주는 것은 아니다. 본격 채택 전 파일 간 심볼 판별, 대표 임베디드 문법, VS Code 내 배포와 실행에 대한 검증이 필요하다.

## 분석 결과를 해석하는 규칙

- 함수 선언과 함수 주소 전달은 References의 서로 다른 위치 종류로 표시하고 직접 호출로 취급하지 않는다. 주석·문자열의 이름 일치는 코드 참조에서 제외한다.
- 함수 식별에는 이름만 사용하지 않고 파일과 정의 위치를 함께 사용한다.
- 파일 내부 static 함수와 지역 변수·매개변수의 이름 가림을 고려한다. 헤더의 static 함수는 포함 맥락에 따라 달라질 수 있어 파일 단위 규칙만으로 연결 대상을 확정하지 않는다.
- 구문상 직접 호출 위치와, 호출 대상 함수의 연결 결과를 별도로 보관한다.
- 여러 제품·보드의 같은 이름 함수가 한 폴더에 있으면 하나를 임의로 고르거나 모두 확정 호출자로 연결하지 않는다. 후보로 구분한다.
- 비활성 영역 제외 옵션이 켜져 있으면 리터럴 `#if 0`의 본문을 제외하고 `#else`를 분석한다. `#if 1`, 리터럴 조건의 `#elif`, 중첩 조건에서도 상위 조건과 앞서 선택된 분기를 고려한다. 제외된 영역의 함수·변수 정의와 호출·참조는 색인에 넣지 않는다. Context는 원본 파일과 원래 줄 번호를 유지한다.
- 빌드 설정이 없는 `#ifdef FEATURE`나 `#if FEATURE`에서 매크로 상태를 모르면 임의로 미정의 또는 0으로 간주하지 않는다. 판정 불명인 분기는 조건 표시와 함께 보존한다. 실제 전처리기에서 미정의 식별자를 0으로 처리하는 규칙과, 분석 도구가 외부 정의 유무를 모르는 상태는 다르다.
- 복합 조건식 및 매크로 값에 따른 평가 범위는 별도 검증이 필요하다. 지원하지 않는 조건은 판정 불명으로 두며, 전체 전처리기를 구현한 것으로 간주하지 않는다. 옵션 변경 시 색인과 그래프를 갱신한다.
- 함수 포인터 호출은 간접 호출로 구분한다. 알려지지 않은 포인터 대상을 특정 함수의 호출자로 만들어 넣지 않는다.
- 매크로 호출과 매크로가 확장되어 발생하는 함수 호출은 별도 문제다. 첫 버전은 전처리기 전체를 구현하지 않으며, 확장으로 생기는 관계의 누락 가능성을 기능 설명에 명시한다.
- 컴파일러 전용 문법 등으로 구문 분석이 불완전하면 해당 파일의 분석 상태를 표시한다. 이를 호출 관계가 없다는 결과와 구분한다.

## 최소 구현 구조

1. 파일 분석: 함수 정의, 선언, 호출 구문, 함수 참조, 범위, 조건부 컴파일 맥락을 수집한다.
2. 관계 인덱스: 호출·참조 위치와 대상 후보를 연결하고 관계 종류별 조회를 제공한다.
3. VS Code 연결과 두 뷰: 심볼 선택, 깊이 제한, 노드 확장, Context 미리보기, 명시적인 메인 코드 이동을 처리한다. 양쪽 뷰가 같은 파일·위치 정보를 사용한다.

파일 검색과 분석은 UI를 막지 않도록 수행한다. 파일 생성·수정·삭제 및 열린 문서의 미저장 변경을 반영하고, 오래된 분석 응답이 최신 선택을 덮어쓰지 않도록 한다. 그래프의 부분 결과, 분석 중, 잘린 결과를 구분한다. 큰 그래프는 노드 수 제한과 추가 펼치기를 사용하되 제한값은 실제 측정 후 결정한다.

## 검증 순서와 합격 기준

1. 분석 기술 검증: 빌드 설정이나 언어 확장 없이 작은 C 소스 폴더에서 함수와 직접 호출 위치를 얻는다.
2. 정확성 검증: 파일을 넘는 호출, 같은 이름 static 함수, 이름 가림, 선언·주석·문자열, 함수 주소 전달, 간접 호출, 조건부 분기, 헤더 함수, 매크로, 재귀·순환을 포함한 예제의 기대 결과와 비교한다. 지원하지 못하는 사례는 분리해 기록한다.
3. 탐색 검증: 한 호출자에서 두 번 호출하면 두 위치가 모두 보이고 선택 시 Context에 각각 정확한 코드가 표시된다. 메인 코드의 파일·커서·스크롤 및 그래프 루트는 유지된다. 여러 줄 호출 및 한글이 포함된 파일에서도 위치가 맞아야 한다.
4. 깊이 검증: A → B → C에서 C의 깊이 1은 B, 깊이 2는 A까지 표시한다. B를 선택해 추가 1단계를 확장하면 A가 표시된다. 키보드와 메뉴 조작 결과가 같아야 한다. 순환에서는 무한히 확장되지 않는다.
5. 갱신 검증: 빠른 커서 이동과 관계 노드 선택, 미저장 수정, 저장, 파일 삭제 후 오래된 코드·위치·관계가 남지 않는다. Context 조작으로 Relation의 루트가 바뀌지 않는다. A 본문의 B를 클릭하면 B의 관계를 표시한다.
6. 실사용 검증: 대표 프로젝트에서 최초 분석 시간, 반복 조회 지연, 메모리 사용량을 측정한다. 아직 대표 프로젝트와 규모는 정해지지 않아 성능 수치를 보장하지 않는다.
7. 참조 검증: 함수 선언 및 함수 주소 전달은 References에 표시되고 Callers에서 제외된다. 참조 위치 선택 시 Context의 해당 줄이 강조된다. 동명 후보를 임의의 함수로 확정하지 않는다.
8. 아이콘 검증: 함수 노드와 함수 주소를 보관하는 변수 노드의 아이콘이 다르다. 함수 포인터 변수를 함수로 잘못 표시하지 않는다. 판별 불가능한 항목은 미확인으로 표시하고, 아이콘의 툴팁과 접근성 이름도 실제 종류와 일치한다.
9. 조건부 제외 검증: `#if 0` 안의 정의·호출은 나타나지 않고 대응 `#else`는 남는다. 비활성 상위 분기의 중첩 `#if 1`도 제외된다. 리터럴 조건의 `#elif` 선택, 판정 불명 분기의 유지, 제외 옵션 전환 후 재색인 및 Context 원본 줄 번호를 확인한다. 작은 구문 탐색 예제로 4개 분기 사례는 실행 확인했으며 제품 색인·UI 연동은 아직 미검증이다.
